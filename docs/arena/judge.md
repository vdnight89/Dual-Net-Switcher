# Arena 交叉评审

本次完整阅读了 `WORKLOG.md`、候选 A 与候选 B。这是同模型交叉评审，知道候选来源，且评审者参与了 B 的设计，因此不是盲审，也不是多模型共识。评分针对文档契约的可实现性，不代表 Windows 写入行为已通过实测。

## 评分与结论

按 WORKLOG 权重，单项满分 10 分，加权总分折算为 100 分。

| 标准 | 权重 | A | B | 依据 |
| --- | ---: | ---: | ---: | --- |
| 恢复和所有权 | 30% | 9.0 | 8.5 | 两者均覆盖精确身份、借用、外部漂移；A 明确两种 route store 和接口属性资源，B 类型中尚未补全接口 Metric 资源。 |
| 系统域名解析正确性 | 20% | 9.0 | 8.5 | 都覆盖 NRPT、DNS 路径自举与共享 IP；A 更清楚地规定 on-link、自适应 TTL、CNAME 和 last-good 来源。 |
| 实现与维护简洁 | 20% | 8.0 | 8.0 | A 增加 HTTP 与双语言边界，但 Node 在当前环境现成且测试方便；B 无浏览器鉴权，却需妥善实现 PowerShell UI 异步、UAC 重启与类/模块约束。 |
| 重试崩溃幂等性 | 20% | 8.5 | 8.5 | 两者均依赖系统实际状态判定、逆序补偿和落盘；A 的两阶段域名规划尚需补全协议，B 的 applied/journal 提交协议仍需完整字段。 |
| 可测性 | 10% | 9.0 | 8.0 | A 纯 JS 领域 + Node 内置测试更易运行；B 也有假平台，但当前没有承诺 Pester 可用，测试入口需自行补齐。 |
| **加权总分** | **100%** | **87.0** | **83.5** | A 小幅领先，并非 B 不可行。 |

推荐以 A 为基线。A 更适合当前已安装 Node 的开发环境，界面迭代和纯函数测试更直接；PowerShell 独占系统事务的边界也比让 Node 拼装逐条写命令更深。B 的主要价值是验证“必须本地 HTTP”并非需求约束，同时提供两项应嫁接到 A 的明确规则：自动同步只使用成功应用的配置；DNS 第二阶段必须在执行新增步骤之前扩展并刷新同一事务日志。

B 的零安装优势对普通 Windows 分发用户仍然成立。若项目后来要求在没有 Node 的机器直接运行，应重新评估 B 或打包分发方案，不能把开发机有 Node 等同于所有用户都有 Node。

## A 实现最需警惕的三个问题

### 1. 自动同步不应把“保存的草稿”变成管理员已授权策略

A 的 usage 写了 reconcile 使用“最新配置”，后文却同时保留“已应用 revision”和“未应用更改”。这会出现用户刚保存一个外网网段、尚未审阅预览，定时器就替用户应用的行为。应将配置明确分为 draft revision 和 applied config snapshot；`saveConfig` 只更新草稿，`apply` 成功后才更新 applied。`reconcile` 只能重解析已应用快照中的域名，并针对同一策略重新计算网卡变化；若应用失败，原 applied snapshot 和域名 last-good 必须保留。界面状态也要显示自动同步的是哪个版本。

验收：保存一个新增规则后触发 timer，系统期望资源不得变化；显式应用成功后再触发 timer 才含新规则。保存期间或应用失败后的 timer 同样不得越过边界。

### 2. 两阶段 DNS 自举还缺少真正可执行的事务协议

A 的 `transactWindows({ desired, observedFingerprint })` 看起来要求传入完整期望资源，但域名 IP 要等执行器建立 DNS 路径后才知道。若 Node 在 bootstrap 后自行查询、生成计划再发第二次事务，崩溃窗口会失去一笔操作的所有权；若 PowerShell 自行重复实现规则规划，则 Node 和 PowerShell 会各维护一套冲突逻辑。必须在编码前选定唯一设计：执行器拥有整笔事务的生命周期，允许固定、结构化的阶段输入与计划追加；解析阶段由明确的同一所有者完成，每次追加具体 before/after 步骤均先落盘，再写系统。记录未完成解析阶段，重启可撤销前置资源，不能仅重放“已知步骤”。不得通过开放任意脚本回调绕过固定 action 边界。

验收：在 bootstrap 创建后、解析后、追加日志前后、第一条业务路由写入前后逐点模拟崩溃，重新启动后都应得到完整旧状态或完整已提交新状态；不能留下无所有权的 DNS 路由。

### 3. 资源身份、存储副作用和提交窗口不能仅靠假平台证明

A 对 ActiveStore/PersistentStore 和 compare-and-swap 的认识正确，但 Windows 实际 cmdlet 可能对活动项产生联动，PowerShell JSON 的单项/数组、空值和枚举也容易使指纹漂移。删除 PersistentStore 后活动项是否留下、接口 Metric 修改后实际值是什么、NRPT 本地规则与有效策略的来源如何区分，必须由 Windows 边界规范化后统一定义。“拥有一个持久项”不自动等于“拥有所有匹配活动项”。提交清单与 journal 两份文件必须以 transactionId 和完整 committed payload 明确恢复判定，避免已成功写所有权但旧 applying journal 又回滚的窗口。

验收：假平台覆盖所有写前写后崩溃；Windows 集成检查在隔离环境验证 store 联动和完整快照往返。当前机器只读验证字段和输出格式，不能以只读探测宣称回滚已实测。reset 需验证借用项未删、外部改动项未覆盖、接口原 automatic/metric 均恢复。

## 其他必要实施约束

A 的管理员 HTTP 不是普通开发服务器，首次可写交付前必须落实已写出的 Host/Origin/会话/JSON 校验和文本渲染。登录引导不能因浏览器正常导航而放宽修改接口的 Origin 校验；令牌、会话与数据目录不得进入公开静态目录或日志。token exchange 应具有单次消费语义。属于架构承诺的必要实现，不应推迟到所谓正式版本。

两者均只保证 IPv4 和遵循系统 DNS 的应用；界面必须简明准确说明，不默认禁用 IPv6、不改浏览器 DoH、不写 hosts。路由落盘、计划任务和当前机器默认出口的真实修改仍只能由用户在产品界面显式操作或在隔离测试环境完成。
